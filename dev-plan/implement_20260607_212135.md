이 문서는 `demos/board_rbac` 이식 이후 기존 sibling board 폴더를 삭제해도 되는지 전문가 관점으로 재검토하고, 삭제 범위와 검증 절차를 고정하기 위한 작업 문서다.

## 개발 목적

권한별 board RBAC self-test demo가 `coreline-auth/demos/board_rbac`로 이동한 뒤, 기존 `packages/coreline-board`와 `packages/coreline-board-saas` 폴더를 더 이상 active source로 유지하지 않는 삭제 계획을 진행한다.

최종 목표:

- `coreline-auth`의 실제 self-test source-of-truth는 `demos/board_rbac` 하나로 고정한다.
- `src/coreline_auth`는 계속 board package/import를 모르는 독립 인증 모듈로 유지한다.
- 기존 sibling package 폴더 삭제 전후로 현재 구현 결과가 깨지지 않는지 검증한다.
- 삭제 후 문서가 “sibling package가 남아 있다”는 과거 상태를 계속 말하지 않게 정리한다.

## 개발 범위

- 구현 계획 `implement_20260607_203709.md`의 완료 상태를 재감사한다.
- `coreline-auth` 내부 board legacy 파일/테스트가 제거된 상태인지 확인한다.
- 삭제 후보를 `../coreline-board`, `../coreline-board-saas`로 한정한다.
- 삭제 전 backup tarball을 `/tmp`에 남긴 뒤 폴더를 제거한다.
- README/self-test/dev-plan 문서를 삭제 이후 상태에 맞게 정리한다.
- `coreline-auth` 테스트/빌드/import guard를 다시 실행한다.

## 제외 범위

- `demos/board_rbac`는 삭제하지 않는다.
- `src/coreline_auth/examples/saas_app.py`와 `src/coreline_auth/examples/saas_demo/` auth-only demo는 삭제하지 않는다.
- CoreMCP root의 tracked 파일이나 다른 package는 수정하지 않는다.
- Git history rewrite, `git reset --hard`, force push는 하지 않는다.
- OAuth/OIDC/MFA/WebAuthn/Postgres 등 인증 기능은 이번 삭제 작업에 섞지 않는다.
