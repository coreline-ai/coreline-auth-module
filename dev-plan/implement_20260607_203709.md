## 개발 목적

`coreline-board`에 남아 있는 권한별 게시판 테스트 데모를 `coreline-auth` 레포 안에서 **demo-only**로 다시 한 번에 실행 가능하게 만든다.

최종 목표는 다음 상태다.

- `coreline-auth` 기본 인증 코어(`src/coreline_auth`)는 계속 독립 인증 모듈로 유지한다.
- 게시판 데모는 `coreline-auth`의 제품 기능이 아니라 인증/RBAC/세션 검증용 **in-repo demo fixture**로 둔다.
- 기존에 가능했던 권한별 계정 선택 테스트를 보존한다.
  - `owner-board@example.com`
  - `admin-board@example.com`
  - `moderator-board@example.com`
  - `author-board@example.com`
  - `user-board@example.com`
  - `viewer-board@example.com`
  - 공통 비밀번호: `coreline-demo-password`
- 한 명령으로 실행 가능한 standalone 진입점을 제공한다.
  - `make run-demo-board`
  - `make smoke-demo-board`
- `make run-demo`는 기본 auth-only 의미를 유지한다. `CORELINE_AUTH_DEMO_INCLUDE_BOARD=true` 방식의 opt-in mount는 이번 goal의 구현 범위가 아니라 후속 후보로만 문서화한다.
- `coreline-board`와 `coreline-board-saas`는 즉시 삭제하지 않고, migration/deprecation 경로를 둔다.

## 문서 기반 제약 사항

- `Coreline Auth는 CoreMCP 하위 기능이 아니라 독립 인증 모듈`이다.
- `src/coreline_auth`는 `coremcp.*` 또는 `apps.api.coremcp.*`를 import하지 않는다.
- `coreline_auth -> coreline_board` 방향 import는 금지한다.
- `coreline_board -> coreline_auth`는 adapter/demo에서만 허용되는 방향이었다. 이번 이식 후에는 demo code가 `coreline_auth`를 소비하되, auth core는 demo code를 몰라야 한다.
- password/session/magic-link token 원문을 DB/log/audit에 저장하지 않는다.
- 자체 암호 알고리즘을 만들지 않는다.
- board service/storage API는 raw session token을 직접 받지 않고 `BoardActor` 같은 principal DTO만 받는다.
- board-owned role vocabulary(`author`, `moderator`)는 auth role enum이 아니라 demo role mapping에서만 유지한다.

## 전문가 판단 요약

### 리뷰 판정

**판정: 업데이트 후 구현 착수 가능.**

초안은 방향은 맞았지만 “한큐에 작업 가능한 수준” 기준으로는 몇 가지 열린 선택지가 남아 있었다. 이번 리뷰에서 아래 결정을 고정한다.

| 리뷰 항목 | 초안의 위험 | 업데이트 결정 |
|---|---|---|
| 실행 방식 | bridge, in-repo demo, opt-in mount가 동시에 열려 있어 구현자가 선택해야 함 | 이번 goal은 standalone `make run-demo-board`만 구현 |
| auth demo 결합 | `saas_app.py`가 board를 lazy import할 가능성 | 이번 goal에서는 auth demo mount 금지 |
| source duplication | `coreline-board`와 `demos/board_rbac`가 동시에 active source가 될 위험 | 이번 goal의 source of truth는 `demos/board_rbac`; sibling packages는 문서상 migration target |
| packaging | `demos/`가 wheel에 들어갈 수 있는지 확인 부족 | `uv build` 후 wheel contents 확인을 필수 테스트로 승격 |
| 테스트 | UX 문자열 확인 중심으로 흐를 위험 | role별 실제 action 권한 테스트를 필수화 |
| guard | `coreline_board_saas` 금지 guard가 빠질 수 있음 | auth source import guard에 명시 추가 |
| 문서 | stale `/board` 문서가 다시 혼선을 만들 위험 | `docs/self-test-webapp.md` 갱신을 완료 조건에 포함 |

### Scope Challenge 결과

1. **이미 존재하는 해결책**: `../coreline-board/src/coreline_board/demo`가 권한별 계정 seed, 로그인 prefill, board route, role mapping을 이미 제공한다. 새 설계보다 이 구현을 demo namespace로 옮기는 것이 맞다.
2. **최소 변경 세트**: `src/coreline_auth` 수정 없이 `demos/board_rbac`, `tests/demos`, `Makefile`, docs만 건드리는 것이 핵심 목표를 만족한다.
3. **복잡도 냄새**: 초안의 opt-in mount까지 포함하면 8개 이상 파일과 여러 앱 조합 경로가 생긴다. 이번 goal에서는 opt-in mount를 defer한다.
4. **완성도 선택**: 단순 계정 목록 표시만으로는 부족하다. role별 action 권한까지 테스트하는 “완전한 작은 lake”를 끓인다.

### 이번 goal의 고정 의사결정

| ID | 결정 | 이유 |
|---|---|---|
| ADR-001 | board demo는 `demos/board_rbac`에 둔다 | `src/coreline_auth` 독립성 유지와 repo-local demo 요구를 동시에 만족 |
| ADR-002 | `make run-demo-board`는 standalone app만 실행한다 | 한큐 실행 가능하면서 auth demo import boundary를 흐리지 않음 |
| ADR-003 | `CORELINE_AUTH_DEMO_INCLUDE_BOARD=true make run-demo`는 후속 후보로만 둔다 | 지금 구현하면 composition/lazy import 리스크가 커짐 |
| ADR-004 | `coreline-board`는 이번 goal에서 삭제하지 않는다 | 기존 wrapper/test 경로를 깨지 않고 migration 안내 가능 |
| ADR-005 | `author/moderator`는 board demo role mapping에만 존재한다 | auth core Role enum 오염 방지 |
| ADR-006 | `/demo-board`를 기본 board prefix로 쓴다 | auth product route가 아닌 demo fixture임을 명확히 함 |

1. **코어 import 금지 유지가 최우선이다.**
   `coreline-auth`에 데모를 다시 둔다고 해서 `src/coreline_auth`가 board를 알면 이전 분리 작업의 의미가 사라진다. demo-only 코드는 repo root의 `demos/` 아래에 두고 package wheel에서 제외한다.

2. **한큐 실행은 Makefile/runner에서 해결한다.**
   dependency 방향을 깨서 `coreline_auth.examples.saas_app`가 board를 import하게 만들기보다, `make run-demo-board`가 `PYTHONPATH=.:src`로 `demos.board_rbac.app:app`을 실행하게 한다.

3. **권한별 계정 선택은 기능 요구사항으로 고정한다.**
   기존 사용성의 핵심은 테스트 계정 존재가 아니라, UI에서 role을 고르고 즉시 로그인/권한 차이를 확인하는 흐름이다. 따라서 테스트도 문자열 존재가 아니라 실제 login → board action 권한 차이를 검증해야 한다.

4. **board role은 demo-local이어야 한다.**
   `author`, `moderator`는 인증 제품의 보편 role이 아니라 게시판 도메인 role이다. `Role("author")`가 계속 실패하는 상태가 올바른 상태다.

5. **점진적 적용은 baseline 확인 → in-repo standalone demo → docs/wrapper 안내 순서가 안전하다.**
   temporary bridge와 auth demo opt-in mount는 이번 goal에서 제외한다. 곧바로 `demos/board_rbac`를 source-of-truth로 만들고, sibling packages는 문서로만 연결한다.

```text
  │ renders selected email + demo password
  │
  │ POST /login
  ▼
CorelineAuthService.login_password()
  │ returns opaque session token
  ▼
HttpOnly demo session cookie
  │
  │ GET /demo-board
  ▼
DemoBoardSessionVerifier
  │ verify_session(token)
  │ map auth role + seeded board role
  ▼
BoardActor(id, email, board_role, status)
  │
  ▼
BoardService.list/create/update/delete(actor, ...)
  │
  ▼
BoardStorage(memory/sqlite)
```

### Role mapping 경계

```text
Auth DB user row
  role = owner | admin | viewer | user
        │
        ▼
Demo seed mapping by user_id
  owner-board      -> owner
  admin-board      -> admin
  moderator-board  -> moderator
  author-board     -> author
  user-board       -> user
  viewer-board     -> viewer
        │
        ▼
BoardActor.role = board-local role
```
